# Pruebas de carga de la API con k6

Los escenarios viven en `tests/load/k6/`, separados del código de producción. Están escritos en TypeScript y usan el alias `@/`; `scripts/run-k6.ts` crea un bundle temporal con esbuild para que k6 pueda ejecutarlos. `config.ts` define los perfiles, `scenarios/` organiza los flujos por endpoint y `api.ts` compone la carga y administra la limpieza.

## Requisitos y ejecución

Instala k6 según la [guía oficial](https://grafana.com/docs/k6/latest/set-up/install-k6/) y abre una terminal nueva. Usa una API key dedicada a pruebas y ejecuta `bun run load:setup`: genera 100 identidades deterministas (`savecloud-k6-user-001` a `savecloud-k6-user-100`) en `.env.k6`, archivo local ignorado por Git. No hace falta registrar las identidades: la API usa `x-user-id` como partición de datos. Las identidades generadas empiezan sin biblioteca; para probar lecturas con datos representativos, configura `USER_IDS` con identidades de un entorno de pruebas que ya tengan guardados. `USER_ID` sigue disponible para simular varios dispositivos en una sola cuenta. El ciclo de escritura usa un prefijo `k6-` por ejecución y lo elimina al terminar.

```powershell
$env:BASE_URL = "http://localhost:3000"
$env:SYNC_GAMES_API_KEY = "<api-key-de-pruebas>"
bun run load:setup
bun run load:smoke
bun run load:steady
bun run load:stress
bun run load:capacity
bun run load:ws
```

En Linux/macOS, exporta las mismas variables. El smoke comprueba `/health` una vez antes de iniciar; todos los perfiles requieren autenticación y ejercitan rutas reales de la API. `bun run load:setup` acepta una cantidad opcional, por ejemplo `bun run load:setup 50`. Para estrés, conviene usar 100 identidades de prueba con bibliotecas preparadas; la prueba imprime la población activa. Para capacidad, prepara hasta 250 identidades con `bun run load:setup 250`. Las variables `USER_IDS` o `USER_ID` definidas en la terminal tienen prioridad sobre `.env.k6`.

## Flujos

Cada iteración selecciona uno de tres flujos con una distribución aproximada de 70/20/10:

1. **Navegación (70 %):** lista `/saves`, consulta `/saves/summary`, abre los respaldos del juego seleccionado y solicita una URL presignada de descarga para un guardado existente. En parte de las navegaciones también revisa papelera, invitaciones pendientes, notificaciones, membresías de nube y clips existentes. La consulta de clips abre sus metadatos con `/api/clips/:clipId`. No descarga archivos ni modifica datos existentes.
2. **URLs presignadas (20 %):** genera URLs de subida simples y batch; no almacena objetos.
3. **Ciclo de guardado (10 %):** obtiene una URL, sube un archivo pequeño directamente a S3, confirma que aparece en `/saves` y lo elimina permanentemente.

El ciclo de escritura usa un `gameId` aislado por ejecución y VU. Lo borra en `finally` tras cada iteración, y `teardown` vuelve a limpiar todos los prefijos al terminar. La consola muestra el `runId`; si se fuerza el cierre del proceso antes de la limpieza, puedes borrar el namespace con:

```powershell
$runId = "<runId-impreso-por-k6>"
$userIds = if ($env:USER_IDS) {
  $env:USER_IDS -split ","
} elseif ($env:USER_ID) {
  @($env:USER_ID)
} else {
  $prefix = if ($env:USER_ID_PREFIX) { $env:USER_ID_PREFIX } else { "savecloud-k6-user" }
  1..100 | ForEach-Object { "{0}-{1:D3}" -f $prefix, $_ }
}
1..100 | ForEach-Object {
  $index = ($_ - 1) % $userIds.Length
  $userId = $userIds[$index].Trim()
  $body = @{ gameId = "k6-$runId-$_"; permanent = $true } | ConvertTo-Json
  Invoke-RestMethod -Method Post -Uri "$env:BASE_URL/saves/delete-game" `
    -Headers @{ "x-api-key" = $env:SYNC_GAMES_API_KEY; "x-user-id" = $userId } `
    -ContentType "application/json" -Body $body
}
```

## Perfiles

| Comando                 | Carga                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `bun run load:smoke`    | 1 VU durante 30 s                                                                                                   |
| `bun run load:steady`   | Sube a 10 VUs, mantiene 3 min y baja                                                                                |
| `bun run load:stress`   | Sube gradualmente a 100 VUs, mantiene la carga y baja                                                               |
| `bun run load:capacity` | Repite los flujos HTTP sin pausa; sube de 5 a 10, 15, 20 y 25 sesiones/s mientras mantiene 25 WebSockets conectados |
| `bun run load:ws`       | Mantiene 10 conexiones WebSocket concurrentes durante 3 min; envía tramas Ping y mide los Pong                      |

Los perfiles `smoke`, `steady` y `stress` esperan entre 2 y 6 segundos por iteración para aproximarse al ritmo de interacción de una persona. El perfil de capacidad conserva la misma mezcla de 70 % navegación, 20 % URLs presignadas y 10 % ciclos completos de subida temporal que `stress`, pero elimina esa pausa para aumentar la concurrencia. En paralelo mantiene 25 conexiones WebSocket durante los cuatro minutos de carga y envía tramas Ping cada 25 segundos, como el cliente de escritorio. Un 20 % de las conexiones simula el ciclo normal de juego: estado inicial `playing`, heartbeat cada 45 segundos y señal de parada al desconectar; las demás permanecen conectadas sin juego activo. Los ciclos de escritura suben un archivo pequeño a S3 y lo eliminan en `finally`; `teardown` también limpia los prefijos de la ejecución. La rampa controla sesiones por segundo, no RPS: cada sesión contiene una cantidad variable de solicitudes. Usa `http_reqs` y `http_req_rate` del resultado de k6 para observar los RPS reales. La prueba dura aproximadamente cuatro minutos y puede llegar a 250 VU HTTP más 25 conexiones WS; k6 puede necesitar más VU si aumenta la latencia. Los umbrales de errores y latencia están en `tests/load/k6/config.ts`; ajústalos al SLO y capacidad del entorno.

El perfil `ws` mide por separado conexiones persistentes. Sube a 10 VUs, mantiene 10 sockets durante 3 minutos, envía tramas de control Ping cada 25 segundos y mide la latencia de las tramas Pong; después cierra cada conexión limpiamente. En local, `WS_BASE_URL` se deriva de `BASE_URL` y agrega `/ws`. Para AWS, configura `WS_BASE_URL` con el endpoint de conexión WSS de API Gateway WebSocket (por ejemplo, el endpoint con el stage; es distinto del endpoint HTTP). La credencial y los identificadores se envían en los parámetros de conexión igual que el cliente de escritorio. Este perfil no crea ni borra guardados.
